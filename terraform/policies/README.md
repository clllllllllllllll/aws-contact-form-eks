# Operator IAM policy drafts

These JSON files are manual IAM policy sources; they are not Terraform-managed IAM resources, and bootstrap Terraform does not load them. Tracking a file alone does not establish effective permissions. The workload and evidence policies were used in the completed deployment; verify their published versions and attachments before another run. The foundation standby policy is prepared but has not been published or applied.

- `bootstrap/`: state-bucket setup and state access.
- `foundation/`: inventory and foundation service drafts.
- `workload/`: IAM provisioning, role writes and workload service drafts.
- `workstation/`: preflight, residual inventory and deployment helper drafts.

The [stage 01 foundation policy source](foundation/deployer-foundation-stage-01.json) combines only the DNS, exact evidence-bucket and three named log-group permissions for `01-base.tfvars` (all three feature flags false). Customer-managed `ContactFormFoundationStage01` was attached for the approved stage. After a partial apply failure, it was updated to include `logs:TagLogGroup` alongside the existing `logs:TagResource`; a fresh plan showed three additions only and the apply succeeded with three added. Stage 01 now has 11 foundation resources in remote state. Confirm whether this temporary policy remains attached and detach it after the completed window. Later foundation stages require separately reviewed refresh + apply drafts. State-backend access is separate.

The trimmed `workstation/preflight-read-policy.json` was attached to the deployer and successfully read the Singapore EC2 Standard On-Demand vCPU quota by CLI. The effective quota is 8 vCPUs. Recheck the quota and effective permissions before any further paid provisioning.

## One-time publication for repeatable workload builds

For repeatable builds, an IAM administrator reviews and publishes the workload and helper JSON as customer-managed policy default versions. The current reusable versions supported the latest deployment after replacing older copies tied to destroyed key, secret, OIDC and relay IDs. Confirm account `203888389134`, Region `ap-southeast-1`, retained hosted zone `Z0153068M1DZTUZ2CE23`, deployer identity, boundaries and service controls before reuse. The policy files are sources only; a commit does not change AWS permissions. Future builds need new Terraform plans and runtime metadata checks, but no generated-ID substitutions when these published versions remain current.

The [network draft](workload/deployer-workload-service-draft-ec2-network.json) includes `ec2:DisassociateAddress` only for project-tagged EIPs. In two full destroy runs, Terraform tried to disassociate a stale association after NAT deletion and EC2 denied the request on `arn:aws:ec2:ap-southeast-1:203888389134:*/*`. The scoped statement did not authorize that request, so one-pass teardown is unverified. The [main README](../../README.md#7-tear-down-only-the-workload) documents the successful fresh-plan recovery. Any broader IAM grant needs separate review and a live test; the policy source alone does not change effective permissions.

The KMS key policy uses a UUID-shaped key ARN and three existing ownership tags for post-create actions. The EKS cluster creation condition accepts only that regional/account key ARN shape; EKS cannot inspect the referenced key's tags in that condition, so verify the effective `kms:DescribeKey` and `kms:CreateGrant` path separately and inspect the exact key in each plan. Keep `CreateGrant` attached only for the required EKS window because the current action set does not constrain the grantee principal. The app-secret policy uses `contact-form/app-*` plus all three existing ownership tags for metadata and deletion; it grants no secret value read/write. The OIDC policy uses the regional EKS issuer path with a 32-character ID, exact request tags at creation, and existing ownership tags for later management. Its initial tag grant rejects conflicting existing ownership tags, and its ongoing management statement cannot tag or untag. It can still tag a **pre-existing provider without conflicting ownership tags** on that path; inventory this path before each apply and stop on any collision. Terraform role trust must still pin the live issuer.

Do not move the temporary `kms:CreateKey` and `kms:TagResource` grants to the durable KMS policy: the generated key ARN requires a wildcard at creation, and a permanent tag grant could mark an unrelated key as eligible for the tag-gated management actions. The app-secret create/tag grants stay in the same temporary first-target policy because an existing secret lacking ownership tags under the prefix could otherwise be tagged into scope. Attach `ContactFormWorkloadBootstrapTemporary` only around the reviewed two-create target and detach it immediately afterward, including on failure. An administrator may retain the reviewed policy **detached** for reuse; no new version is needed on each run. Inspect other regional KMS keys and project-prefix secrets before attaching, and verify new resource ownership after the target. A retained foundation-managed exact-ARN EKS key would remove this temporary key-creation window but requires Terraform lifecycle changes and an explicit decision on its continuing cost; this policy-only change does not implement that alternative.

The helper's `ssm:StartSession` instance permission requires the relay Name and all three workload tags, Singapore Region, and `ssm:SessionDocumentAccessCheck=true` when that key is present; the only allowed document ARN is `AWS-StartPortForwardingSessionToRemoteHost`. Confirm the relay's tags and that the workstation command supplies this document. Route 53 reads and apex `A` record changes target only the retained zone. Check a different instance, an untagged or mistagged relay, `ssm:SessionDocumentAccessCheck=false`, a different document, and a different hosted zone as denied cases. The prior live tunnel required `BoolIfExists` because the context key was absent; this condition alone does not rule out a default shell session, so verify the effective document authorization during the limited helper window. The document itself does not restrict the forwarding destination.

Validate every published JSON, check the [6,144-character managed-policy limit](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_iam-quotas.html), simulate allowed and denied requests, then verify the default version and effective attachment. Local JSON and plan checks alone do not establish AWS authorization. In particular, test the OIDC dependent tag authorization, the SSM document check, and the node-group service-role read before paid provisioning.

## Read-only demo evidence grant

The [runtime inventory policy](workstation/runtime-inventory-policy.json) is saved as **inline policy `ContactFormDemoEvidenceRead` on the existing `contact-form-provisioners` group**. It covers Security Hub findings, ALB listener/target metadata, the project ALB access-log prefix, certificate metadata, the deployer's own managed-attachment list, FSBP subscription status, the named CloudTrail trail, and timestamp-only reads from three project log groups. The CLI evidence and post-teardown inventory reads succeeded with this grant. An inline group policy does not use a managed user attachment slot. Confirm group membership and effective permissions before another run. Some EC2, RDS, ECR, Secrets Manager, ELB and CloudWatch list actions require `Resource: "*"` in Singapore; Security Hub is scoped to the account's Singapore hub, KMS metadata to this account's keys, and S3 listing to the project access-log prefix. Findings and logs may contain unrelated data, so publish only project metadata and synthetic evidence.

For future CLI-only workload rebuilds and project standby, an administrator can install [scoped-self-attachment-policy.json](workstation/scoped-self-attachment-policy.json) as **group inline policy `ContactFormScopedSelfAttachment`**. It permits only `contact-form-deployer` to attach or detach only the exact `ContactFormWorkloadBootstrapTemporary` or `ContactFormFoundationStandby` managed policies on its own user. It grants no ability to create or edit either managed policy. The administrator must verify that both policies exist, their default versions match the [bootstrap draft](workload/deployer-workload-bootstrap-temporary-draft.json) and [standby draft](foundation/deployer-foundation-standby.json), and the group's total inline-policy size is within quota. This trades an administrator at each run for a standing, narrowly scoped self-attachment ability; treat it as an assignment-only IAM exception and remove it when repeatable demonstrations are no longer needed. Attach Bootstrap only around its first target and Standby only around the reviewed pause/resume plan. [AWS documents the `iam:PolicyARN` restriction](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_controlling.html).

From the repository root, copy the reviewed document for the IAM Console:

```bash
cat terraform/policies/workstation/runtime-inventory-policy.json | clip.exe
```

After the administrator saves the inline policy, test it with `aws securityhub get-findings --region ap-southeast-1 --max-results 1` and, after teardown, `python scripts/check_residual.py --profile contact-form-deployer` from the assignment virtualenv. An empty finding list is not a passing control; a residual inventory with denied reads remains inconclusive. The policy file alone does not grant access.

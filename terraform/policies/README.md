These JSON files are manual IAM policy sources; they are not Terraform-managed IAM resources, and bootstrap Terraform does not load them. Tracking a file alone does not establish effective permissions. The stage 01 foundation policy was published and attached for its approved 27 September 2026 apply; later policy drafts still need their own review and attachment windows.

- `foundation/`: inventory and foundation service drafts.

## One-time publication for repeatable workload builds

An IAM administrator must review and publish the current workload and helper JSON as customer-managed policy default versions. Previously published copies contained exact ARNs for a destroyed key, app secret, OIDC provider and relay; replace those copies **once** with the reusable drafts. Confirm account `203888389134`, Region `ap-southeast-1`, the retained hosted zone `Z0153068M1DZTUZ2CE23`, the deployer identity, existing permissions boundary and service controls. The policy files are sources only; a commit does not change AWS permissions. Future clean workload destroys and rebuilds need new Terraform plans and runtime metadata checks, but **no generated-ID substitutions or policy-version changes** when these drafts remain current.

The [network draft](workload/deployer-workload-service-draft-ec2-network.json) adds `ec2:DisassociateAddress` for owned Singapore EIPs under the existing Project/Lifecycle resource-tag guard. AWS lists EIP resource and tag-condition support for this action. The API takes an `AssociationId`, which EC2 must resolve to the tagged EIP for this statement to match. The last denial named `arn:aws:ec2:ap-southeast-1:203888389134:*/*` after NAT deletion; if that is the authorization resource for a stale association, this scoped statement will still deny. AWS also lists a network-interface resource for the action, which this existing owned-network statement does not include; effective authorization must be checked before assuming the EIP ARN is sufficient. Simulate the revised grant, use an authorized `--dry-run` on an active project association, and verify a future teardown before claiming one-shot cleanup. A region-wide `Resource: "*"` grant is not included. The KMS key policy uses a UUID-shaped key ARN and three existing ownership tags for post-create actions. The EKS cluster creation condition accepts only that regional/account key ARN shape; EKS cannot inspect the referenced key's tags in that condition, so verify the effective `kms:DescribeKey` and `kms:CreateGrant` path separately and inspect the exact key in each plan. Keep `CreateGrant` attached only for the required EKS window because the current action set does not constrain the grantee principal. The app-secret policy uses `contact-form/app-*` plus all three existing ownership tags for metadata and deletion; it grants no secret value read/write. The OIDC policy uses the regional EKS issuer path with a 32-character ID, exact request tags at creation, and existing ownership tags for later management. Its initial tag grant rejects conflicting existing ownership tags, and its ongoing management statement cannot tag or untag. It can still tag a **pre-existing provider without conflicting ownership tags** on that path; inventory this path before each apply and stop on any collision. Terraform role trust must still pin the live issuer.

Do not move the temporary `kms:CreateKey` and `kms:TagResource` grants to the durable KMS policy: the generated key ARN requires a wildcard at creation, and a permanent tag grant could mark an unrelated key as eligible for the tag-gated management actions. The app-secret create/tag grants stay in the same temporary first-target policy because an existing secret lacking ownership tags under the prefix could otherwise be tagged into scope. Attach `ContactFormWorkloadBootstrapTemporary` only around the reviewed two-create target and detach it immediately afterward, including on failure. An administrator may retain the reviewed policy **detached** for reuse; no new version is needed on each run. Inspect other regional KMS keys and project-prefix secrets before attaching, and verify new resource ownership after the target. A retained foundation-managed exact-ARN EKS key would remove this temporary key-creation window but requires Terraform lifecycle changes and an explicit decision on its continuing cost; this policy-only change does not implement that alternative.

The helper's `ssm:StartSession` instance permission requires the relay Name and all three workload tags, Singapore Region, and `ssm:SessionDocumentAccessCheck=true` when that key is present; the only allowed document ARN is `AWS-StartPortForwardingSessionToRemoteHost`. Confirm the relay's tags and that the workstation command supplies this document. Route 53 reads and apex `A` record changes target only the retained zone. Check a different instance, an untagged or mistagged relay, `ssm:SessionDocumentAccessCheck=false`, a different document, and a different hosted zone as denied cases. The prior live tunnel required `BoolIfExists` because the context key was absent; this condition alone does not rule out a default shell session, so verify the effective document authorization during the limited helper window. The document itself does not restrict the forwarding destination.

The default IAM user quota is ten customer-managed policy attachments. Six workload service policies and the two IAM policies occupy eight; the helper occupies a ninth, and one of temporary bootstrap, preflight or runtime inventory occupies the tenth. State access is recorded as an inline policy and uses no managed slot. An administrator checks actual direct and group grants and rotates completed foundation or optional attachments rather than assuming the recorded state is still current. Validate every published JSON in the IAM Console or Access Analyzer, check the [6,144-character managed-policy limit](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_iam-quotas.html), simulate allowed and denied requests, then verify the default version and effective attachment. Local JSON and plan checks alone do not establish AWS authorization. In particular, test the OIDC dependent tag authorization, the SSM document check, and the node-group service-role read before paid provisioning.
